# Android 客户端（前端）编码 Agent 提示词

把下面内容完整交给负责 Android 客户端的编码 Agent。已经确定的产品决策不用再问用户；实现中拿不准的地方按本文和契约先做，并记到 `AI anti lie/docs/android-progress.md`。

## 背景和目标

这是参加大学生竞赛的作品「AI 智能反诈系统」。本期只做其中的方案 B「一键鉴诈」：用户觉得聊天不对劲时，在手机上点悬浮球截屏，或者把截图、文字、链接分享给本 App，几秒内拿到一份鉴诈报告：是不是诈骗、哪种套路、对方哪几句话有问题、有没有相似的公开案例、现在该怎么办。

你负责 Android 客户端，代码放在 `AI anti lie/android/`。鉴诈服务（后端）由另一个 Agent 在 `AI anti lie/server/` 开发，两边只通过 `AI anti lie/docs/api-contract.md` 对接，这份契约是唯一权威。

后端不部署到云服务器，而是跑在团队的笔记本上。演示手机用数据线连着笔记本，笔记本上执行 `adb reverse tcp:8000 tcp:8000` 之后，手机访问自己的 `127.0.0.1:8000` 就是访问笔记本上的服务。对 App 来说，后端只是一个地址可配置的 HTTP 服务，App 自己不需要知道 adb 的存在。

做取舍时记住这几件事：

- 这是整个参赛项目的保底层，3 周内必须完整可演示。答辩时评委会随手发一张聊天截图过来现场鉴定，所以「从点一下到看到报告」这条路径的稳定和顺畅，比功能数量重要。
- 使用者可能正处在被骗的过程中，也可能是老人。界面要让人一眼看懂结论和下一步，不需要读完整页。
- 隐私是这个作品的核心卖点之一：聊天原文只在手机上处理，上传的只有脱敏后的文字，而且用户在上传前能看到会上传什么。
- 国内大多数 Android 手机没有 Google 服务，所以不能依赖 GMS、Firebase 和 ML Kit。
- 这里写的文本归一化、脱敏和规则引擎，之后会被项目的其他部分（被动监听聊天、付款前拦截）复用，所以要做成不依赖 Android 的纯 Kotlin 模块。

## 开始前

1. 完整阅读 `AI anti lie/docs/api-contract.md`。
2. 执行并记录 `pwd`、`git rev-parse --show-toplevel`、`git status --short --branch`。
3. 仓库陷阱：这个 git 仓库的根是用户主目录（如果你在 worktree 里，根就是 worktree 目录），里面还有一个不相干的项目，主目录下还有大量未跟踪文件。本项目的一切都在 `AI anti lie/` 下。提交只用显式路径，不用 `git add .` 或 `git add -A`；不改动 `AI anti lie/` 之外的任何文件；不执行 `git clean`、`git reset --hard`。
4. 检查构建环境：JDK 17 及以上、Android SDK（`ANDROID_HOME`）、`adb devices` 是否有真机或模拟器。2026-11-11 检查时，这台 Mac 上 JDK、Android Studio、Android SDK 和 adb 都还没有装。缺少时停下来告诉用户需要安装什么，不要自己去装大体积的工具链。Android Studio 自带 JDK 并提供 SDK 管理器；Homebrew 里有 `android-studio` 和 `android-platform-tools`。
5. 网络情况（同一天检查，开工时请重新确认）：Google 的 SDK 下载地址和 Maven 仓库、Maven Central、Gradle 官方下载地址都能连通；从 GitHub Release 下载文件会超时。依赖下载慢或失败时，在 `settings.gradle.kts` 里配置国内 Maven 镜像。

## 技术栈

| 用途 | 选型 | 说明 |
| --- | --- | --- |
| 语言与界面 | Kotlin、Jetpack Compose、Material 3、单 Activity + Navigation Compose | 版本用当前稳定版，集中写在版本目录（`libs.versions.toml`） |
| 架构 | MVVM、Hilt、Coroutines / Flow | |
| 网络 | Retrofit + OkHttp + kotlinx.serialization | 遇到不认识的枚举值要有兜底，不能崩溃 |
| 本地数据 | Room（鉴定历史）、DataStore（设置） | 只存脱敏后的文字和报告 |
| 图片 | Coil | |
| 悬浮球 | `Petterpx/FloatingX` 3.0.0（MIT）的 `floatingx-system` 和 `floatingx-compose` | 系统级悬浮窗、权限申请、拖动吸边、Compose 内容都已经做好 |
| 端侧 OCR | `RapidAI/RapidOcrAndroidOnnx`（Apache-2.0）发布的 `OcrLibrary-1.3.0-release.aar` | 模型是 PaddleOCR 的中文模型；用法见下文 |
| 二维码 | ZXing `core`（Apache-2.0） | 从截图里解出二维码链接 |
| 测试 | JUnit、kotlinx-coroutines-test、OkHttp MockWebServer、Compose UI Test | |
| 系统版本 | `minSdk` 26，`targetSdk` 取国内应用市场当前要求的版本 | |

工程分两个 Gradle 模块：

- `:engine`：纯 Kotlin/JVM 库，不依赖 Android。放文本归一化、脱敏、聊天版面还原、规则引擎、链接提取和契约数据类。这部分逻辑最容易出错，放在这里可以用普通 JVM 单元测试几秒钟跑完。
- `:app`：界面、系统接口、OCR、网络、存储。

可以参考的现成项目：`android/nowinandroid`（Apache-2.0）的 Compose + Hilt + 版本目录写法。它的多模块拆分对 3 周的项目来说太重，只参考写法，不照搬结构。

关于 OCR 库要先知道的事：这个 aar 是 2023 年 2 月发布的，自带 onnxruntime 和模型，接口很简单（`OcrEngine(context).detect(bitmap, outBitmap, maxSideLen)`，返回每个文本块的文字和四角坐标），是最省事的选择。但它的原生库比较旧，所以第一周就要在演示用的真机上验证能不能加载、识别速度是否可接受。请把 OCR 藏在一个接口后面。如果这个 aar 在目标机器上不能用，退路是用 Maven 上的 `com.microsoft.onnxruntime:onnxruntime-android` 加 RapidOCR 提供的 PP-OCR 移动端 ONNX 模型自己封装检测和识别两步。aar 体积较大，不要提交进 git：写一个下载脚本，从 GitHub Release 取文件并校验 SHA-256。这台 Mac 当前的网络下载 GitHub Release 会超时，所以脚本要支持走代理，也要支持队员用别的网络下载后手动放到指定位置；文件不存在时，构建要明确说出缺哪个文件、该放到哪里。

## 功能范围

P0，必须完成：

1. 首次引导：说明这个 App 做什么、哪些数据会离开手机，逐项申请权限。
2. 四个送检入口：悬浮球截屏；从其他 App 分享文字或图片过来；在 App 内粘贴文字或输入链接；在 App 内从相册选截图。
3. 端侧处理：OCR、还原聊天顺序和说话人、文本归一化、脱敏、本地规则初筛、二维码识别。
4. 上传前预览：让用户看到将要上传的脱敏文字，可以删掉不想上传的行。
5. 提交、进度展示、鉴诈报告页。
6. 鉴定历史。
7. 网络失败时的本地初判。
8. 设置页和隐藏的开发者选项。

P1，P0 稳定之后再做：

- 语音和视频文件送检（上传前单独征得同意，见契约第 2 节）。
- 在任意 App 里选中文字后出现的「鉴诈」菜单（`ACTION_PROCESS_TEXT`）。
- 用户反馈「是诈骗 / 不是诈骗」。
- 规则热更新。
- 快捷设置磁贴、把报告存成图片分享给家人。

## 各部分要求

### 连接笔记本上的服务

- 默认服务地址是 `http://127.0.0.1:8000`，可以在开发者选项里改。备用连接方式是手机开热点、笔记本连热点，这时地址要改成笔记本的局域网地址。
- 明文 HTTP 的放行范围按契约「运行形态」一节：所有构建都允许访问本机回环地址（`127.0.0.1` 和 `localhost`），调试构建额外允许任意地址，其余一律 HTTPS。用网络安全配置实现。注意 `debug-overrides` 只管证书信任、不管明文开关，调试构建的放行要用 debug 源集里单独的配置文件。路演用调试构建。
- 连接超时设短（2–3 秒）。没做端口转发时连接会立刻被拒绝，局域网地址不通时则会一直挂着。两种情况都要让用户很快看到本地初判，而不是长时间转圈。
- 首页显示服务连接状态：进入首页和回到前台时请求一次健康检查接口，显示「已连接」或「未连接」。未连接时不拦着用户送检，照常走本地初判。
- 健康检查返回 `mock: true` 时，在首页、进度页和报告页都显示醒目的「模拟数据」标记。模拟模式下的报告是写死的示例，不能让人误以为是真实鉴定结果。
- 开发者选项里放一个「连接诊断」：显示当前地址、健康检查的结果和耗时、服务版本、规则版本、大模型状态。连不上时给出排查提示：数据线是否接好、笔记本上是否执行了端口转发、服务是否已启动。队员上台前靠它确认一切就绪。
- 在模拟器上开发时，同样可以用 `adb reverse`，或者把地址改成 `10.0.2.2`。
- 首次引导和隐私说明要如实写数据去向：脱敏后的文字会发到团队笔记本上运行的鉴诈服务，再由它发给大模型服务商；截图原图和未脱敏的文字不离开手机。

### 送检入口

- 分享：注册 `ACTION_SEND` 和 `ACTION_SEND_MULTIPLE`，接收 `text/plain` 和 `image/*`，多图最多 8 张。用户最常用的路径是「系统截图 → 分享 → 选本 App」，这条路径要专门测。
- 微信不允许把聊天文字或语音消息直接分享给其他 App，所以对微信聊天来说，截图是唯一现实的入口。不要设计依赖「从微信分享文字或语音」的流程。
- 分享进来的文件只在处理期间读取，需要落盘时放在 App 私有缓存目录，处理完删除。

### 悬浮球与截屏

用户的期望是：在聊天界面点一下悬浮球，几秒后看到报告，中间不离开聊天界面太久。

- 用户在 App 里打开悬浮球开关时，申请悬浮窗权限和一次屏幕录制授权，并启动 `mediaProjection` 类型的前台服务。
- 授权后保持这一个录屏会话，但空闲时不接收画面：平时把 `VirtualDisplay` 的输出置空，用户点击悬浮球时才挂上 `ImageReader`，拿到一帧立即摘掉。这样每次鉴定只需要点一下，同时可以如实告诉用户「只有点击那一刻的画面会被读取」。
- 截屏前先隐藏悬浮球，等一帧再取图，否则球会被截进去。
- 截图只留在内存或 App 私有缓存里，OCR 完成后立即丢弃，不写入相册。
- 已知的平台限制，请对照当前官方文档核实，这些规则几乎每个大版本都在变：
  - Android 14 起，一次授权只能创建一次虚拟显示，授权结果不能重复使用；必须先拿到用户同意，再启动前台服务，再获取 `MediaProjection`。
  - 用户可以随时从状态栏停止录屏，较新的系统在锁屏时也会自动停止。收到停止回调后把悬浮球标成「需要重新授权」，下次点击时重新申请。
  - 带安全标记的窗口（银行 App、部分支付页面）截出来是黑的。检测到全黑画面时告诉用户改用系统截图后分享。
  - 小米、OPPO、vivo、荣耀等系统对悬浮窗和后台弹出界面有各自的开关。做一个权限自检页，列出每项权限的当前状态和跳转入口。

### 端侧文本处理（`:engine` 模块）

按这个顺序处理，每一步都有单元测试：

1. OCR 得到文本块和坐标。
2. 版面还原：去掉顶部状态栏和标题栏、底部输入栏的内容；把文本块按位置合并成气泡，按从上到下排序；按气泡在屏幕上的横向位置判断说话人，靠左是对方，靠右是用户本人，居中的短文本（时间、系统提示）是 `system`，判断不了就是 `unknown`。说话人很重要：服务端主要分析对方说的话。
3. 归一化：Unicode NFKC、去掉零宽字符、按规则文件里的短语表替换（「薇信」→「微信」）。只做短语级替换。
4. 脱敏：规则和顺序严格按契约第 2 节。URL 整体不动；身份证号和银行卡号要过校验位，避免把普通长数字误伤；必须幂等。
5. 本地规则初筛：加载规则文件，对每一行做正则匹配，得到命中的规则和意图。规则最多几百条，直接用 Kotlin 的 `Regex` 就够，不需要多模式匹配算法。
6. 链接提取：从文字里提取链接；用 ZXing 从截图里解二维码，解出来的链接作为 `origin` 为 `qrcode` 的 `url` 条目。

规则文件：构建时把 `AI anti lie/shared/rules.json` 拷进 assets（这个文件由服务端 Agent 维护）。它还不存在时，用你自己放在 assets 里的一份小的起步规则，内容取契约 4.5 的示例，保证不被对方的进度卡住。

上传的 `text` 就是归一化并脱敏之后的文字，报告页展示的也是这份文字，这样服务端返回的引文一定能在界面上的原文里找到。

### 上传前预览

展示将要上传的脱敏文字（按说话人分左右），用户可以删掉某几行，然后点「开始鉴定」。这一步同时是给用户纠正 OCR 明显错误的机会，也是答辩时讲隐私设计的现成素材。设置里提供「跳过预览直接鉴定」，默认关闭。

### 提交与进度

- 按契约 4.2 提交，按返回的 `poll_after_ms` 轮询。
- 等待期间不要只放一个转圈：把话术、链接、案例、深伪、汇总五个分析器逐项点亮，本地规则初筛命中的内容先展示出来。这是现场演示时评委盯着看的几秒钟。
- 客户端总超时 30 秒。超时或失败时保留 `check_id`，允许重试；用户中途离开页面时任务继续，结果写入历史。

### 报告页

这是整个 App 最重要的一屏。信息顺序按用户的需要排，不按数据结构排：

1. 结论：图标、`headline`、风险等级。分数作为次要信息。
2. 现在该怎么办：`advice` 和 `actions`。高风险时这一块紧跟结论。拨打 96110 用 `ACTION_DIAL` 调起拨号盘，不申请直接拨打电话的权限。
3. 证据：把对话按聊天气泡的样子还原出来，有问题的句子高亮，旁边标出意图名称和解释。没有问题的句子可以折叠。
4. 链接：域名、风险等级、用中文写的原因（例如 `domain_age_lt_30d` 显示为「域名注册不到 30 天」）。
5. 相似案例：标题、摘要、来源名称，点击后在外部浏览器打开来源。`synthetic` 为 `true` 的必须标注「示例」。
6. 降级说明和免责声明：`degraded` 里的每一项翻译成用户能懂的话，例如「链接情报暂时查不到，本次没有检查链接信誉」。

需要守住的几条：

- 对方发来的可疑链接在任何界面都只显示为不可点击的文字。这个 App 不能成为用户点开诈骗链接的入口。
- 服务端返回的文字一律当纯文本显示。只有 `open_url` 动作和案例来源链接可以打开，并且只允许 http 和 https。
- `low_risk` 显示为「暂未发现明显诈骗特征」，旁边要有「如果对方要求转账、垫付或下载应用，仍然要小心」一类的提醒。任何界面都不出现「安全」「可以放心」的说法。
- `inconclusive` 时引导用户补充更多聊天内容。

### 历史与本地数据

- Room 里存：时间、脱敏后的行、报告 JSON、状态。默认保留 30 天后自动清理，用户可以单条删除和一键清空。
- 不保存截图原图和未脱敏的文字。
- 关闭系统备份，避免历史被云备份带走。

### 网络失败时

联不上鉴诈服务时不要只显示错误。展示本地规则初筛的结果，明确标注「未联网，仅本地规则初判」，最高只给到「可疑」，同时给出通用的防骗建议和 96110 入口，并提供重试。

### 设置与开发者选项

- 设置：悬浮球开关、跳过预览、历史保留时间、权限自检、隐私说明、开源许可。
- 开发者选项（连续点击版本号进入）：服务地址、访问令牌、连接诊断、最近一次请求的 `trace_id`。比赛现场可能临时从数据线换成热点，服务地址必须能在不重新打包的情况下修改。
- 服务地址默认是 `http://127.0.0.1:8000`。访问令牌的默认值从 `local.properties` 注入到 `BuildConfig`，不提交进仓库。

## 界面与文案

- 全部文案为简体中文，用口语，不用技术词。写给一个着急的人或者一位老人看。
- 气质上像一位冷静可靠的朋友，不像恐吓式的警示海报。高风险要醒目，但不要整屏大红。
- 风险等级不能只靠颜色区分，要同时有图标和文字。
- 支持系统字体放大到 200% 不截断、不重叠；可点击区域不小于 48dp；主要元素有读屏描述。
- 进度页和报告页请认真设计和打磨：过渡动画、证据高亮的呈现、各种状态（加载、空、失败、降级）都要考虑到。这两屏决定演示效果。
- 给报告页的每一种 `verdict` 准备 Compose 预览，数据用契约里的示例。

## 测试

`:engine` 的单元测试是重点：

- 归一化：全角、数学字母数字、零宽字符、短语替换，以及「威胁」这类不该被替换的词。
- 脱敏：手机号、银行卡号（校验通过与不通过）、身份证号、金额；URL 里的数字不被误伤；重复执行结果不变。
- 版面还原：用构造的文本块坐标测试左右说话人、居中的时间、多行气泡合并、群聊昵称。
- 规则匹配和链接提取，包括不带协议头的链接。
- 契约：把契约文档里的每个示例 JSON 存成测试资源，确认能解析；再加一个带未知枚举值和未知字段的例子，确认不崩溃。

`:app`：

- 用 MockWebServer 测提交、轮询、超时、各类错误码和重试。
- 连接状态：已连接、连接被拒绝、连接超时三种情况，以及 `mock: true` 时「模拟数据」标记出现。
- ViewModel 的状态流转。
- 报告页在四种 `verdict` 和降级状态下的 Compose 界面测试。

不要使用任何真实的私人聊天截图。版面还原用构造的数据测试；真机上需要的测试截图由团队用测试账号按公开案例自己制作，在 `android/testdata/README.md` 里写明放在哪里、怎么用。

## 实现顺序

每一步结束时工程都能构建、测试都能通过：

1. 工程骨架、两个模块、契约数据类和示例解析测试。
2. `:engine` 的归一化、脱敏、规则、链接提取。
3. 网络层，对着服务端的 `MOCK_MODE` 走通「粘贴文字 → 预览 → 提交 → 进度 → 报告」。服务端还没好时用 MockWebServer 和契约示例先做。
4. 报告页和进度页打磨。
5. OCR 接入和版面还原，走通「相册选图」和「分享图片」。
6. 悬浮球和截屏。
7. 历史、设置、开发者选项、权限自检、首次引导。
8. 失败和离线路径。
9. P1。

第 5 步的 OCR 真机验证尽量提前做，它是最可能出意外的一环。

## Git 要求

- 在功能分支上开发，例如 `feature/antifraud-android`。
- 每完成一个能独立验证的功能就提交一次，用 Conventional Commits，例如 `feat(android): add screenshot capture via floating ball`。
- 需要改契约时，先改 `docs/api-contract.md` 并单独提交，在提交说明里写清对服务端的影响。
- `.gitignore` 要覆盖构建产物、`local.properties`、下载的 aar 和模型文件。

## 完成定义

同时满足才算完成，并在 `docs/android-progress.md` 里逐条写明实际验证方式：

1. `./gradlew :engine:test :app:testDebugUnitTest :app:assembleDebug` 全部通过。
2. 在真机或模拟器上实际走通过四个送检入口，写明机型和系统版本。其中至少一次是真机用数据线连着笔记本上的服务走通的。
3. 写明没做的、没验证的和已知风险。尤其是只能在真机上验证的部分：OCR 库能否加载、录屏授权流程、各厂商的悬浮窗权限。没有设备可用时，明确说这些还没有验证过，不要用「构建通过」代替。
